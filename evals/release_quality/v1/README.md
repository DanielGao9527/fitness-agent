# 发布质量协议 v1

这是现有知识更新链的正式检索验收输入，不是新的检索方案，也不代表已经验收。

- 复用既有 260 QA 的 test 划分，固定数据哈希、候选 20、RRF k=60、实际 Top 10。这复用的是历史 test 分组，不宣称全新未见盲测；独立复核指另行审阅相关性标签。当前标签仍是自建标签，`review_status=pending_review`，未经独立相关性复核，禁止批准生产版本，也不会运行留出排名来调参。
- 完成真实独立复核后，由维护者核对标签、保留复核证据并提交其 SHA-256 与 reviewed 状态。哈希用于绑定版本，不能从技术上证明“独立复核”这件事发生过；需要可信的实际审阅记录，不能为了通过测试填任意值。
- 检查仅使用同身份、维度的公开问题向量缓存，不触发云编码。缺缓存、模型/分词器/来源不匹配、证据失效或降级均不批准。空 qrels 不用于判断回答或拒答是否正确。
- 每个可答题 Recall@6、MRR@10 均不退化，候选平均 Recall@6 还须至少 0.80，避免零分与零分也通过。0.80 是预先选定的验收门槛，不是实验结果或提升率。摘录别名不能刷分，排名位置不补齐。
- 报告由服务端计算，绑定来源构建、登记版本、协议/标签哈希及问题缓存哈希；客户端只能引用当前报告，不能上传 `passed=true`。随后仍须人工批准和明确切换。

使用 `scripts/prepare_release_queries.py --database <已有私人库绝对路径>` 查看计划，无网络、无编码。只有完成独立标签复核后，显式追加 `--live --max-calls <次数> --max-input-chars <字符数>` 才会生成公开问题编码；不编码文档、不读取业务正文。失败计入预算并留无原文的私人凭据，不自动重试；确认旧尝试后才能以新预算重跑。服务端发布检查始终只读缓存。

本轮隔离流程使用 tests 内明确标记的合成协议/向量，证明批准、切换、回滚、引用失效和额度接线。它们不属于独立标注或真实语义质量证据；正常应用没有测试绕过开关。回答正确性、真实记忆和单/两轮检索效果仍按 ROADMAP 第 2 步验收。
