## 2. 按依赖顺序推进

### 第一步：E2c/d，完成个人记忆的来源与失效管理

**最终行为：**新会话能够采用已确认且仍有效的个人条件；更正、撤销和到期后不再采用旧条件；页面能解释本次条件来自哪里。

在现有表和服务上补齐：

- 将开放表达产生的记忆作为结构化候选，带原消息/轮次、字段、作用范围、时间语义和确认状态；复用既有理解调用，先覆盖器械与交流偏好。候选不等于事实，自动理解不直接修改长期档案。
- 区分“今天只有哑铃”与“平时在家只有哑铃”；无法判断时澄清。当前有限句式仍保留为确定性路径，不将它称为完整的语义抽取。
- 为被管理的字段记录单调递增版本、来源与替代关系；同一事实只保留一个当前权威入口。器械等已存在字段继续由档案负责，不再在温记忆表存第二份竞争的有效值。
- 本轮条件绑定当时的档案字段版本；档案更正、撤销和清空后令旧上下文及建议失效。覆盖 A→B→A 的更正，不能只靠字符串相等恢复旧临时条件。
- 分清“删除原聊天”与“撤销已确认档案事实”：单独确认保存的档案字段不会因聊天删除而暗中恢复或丢失；历史摘录随来源删除失效。用户明确撤销事实时清除有效值及派生使用，审计事件不额外保留已要求删除的私人正文。
- 审计只写必要来源、版本和状态；用户只能查看本人记忆。新增字段/表按现有迁移、备份和恢复流程交付。

**验收：**不仅检查模型收到什么，还核对新会话最终建议、后续更正后的最终建议、临时条件不跨天、撤销/删除不复活、并发修改拒绝旧结果、重启与跨用户隔离。完成本轮新增确认文案和器械来源的浏览器验收。

**代码入口：**`services/coach_reviews.py`、`coach_memory.py`、`coach_memory_entries.py`、`coach_memory_digests.py`、`training_context.py`、`profile_context.py`、`records.py`，以及 `api/coach.py`、`static/coach-memory.js`、`static/coach.js`。仅在多个入口确有共同逻辑时抽取小型上下文装配函数，不新建通用 Agent 平台。

### 第二步：E3b，完成有界检索恢复与离线回放

**最终行为：**公共资料不足时可以有限地换一种搜索方式；仍无依据就明确停下；来源撤回不能被重试重新引用。

- 延续当前最多两轮的工作流，为初次零候选补设计与接线；改写不得改变原问题的事实目标，不能用搜索弥补用户尚未确认的个人条件。
- 明确区分：公共知识缺失 → 有界重检索；个人事实冲突 → 版本/优先级检查或澄清；引用失效 → 拒绝旧引用、必要时在剩余预算内找有效证据。不能把三种问题都交给“再搜一次”。
- 统一轮次、总云调用数、超时、重复候选和同义改写的终止规则；口语前置理解与检索调用分别计数，均进入已有认证额度。
- 保留公开候选 ID、来源版本、策略版本、停止原因、延迟/调用量等最小轨迹。评测回放使用合成或经过明确选择、脱敏的样本，不默认把私人生产对话收集成训练集。
- 用同一题集与资料版本对比单轮和有界两轮，比较最终证据/答案、无依据拒答以及额外延迟与调用成本。先验证固定策略；失败分析只产生策略候选，不让模型直接修改运行参数。

**验收：**有候选但不充分、零候选、重复候选、改写偏题、资料在回答期间撤回、额度耗尽及超时均可重放；第二轮对原问题判断且不得绕过个人限制。提供真实模型小批联调和独立留出报告，报告负收益题。

**代码入口：**`services/knowledge_answers.py`、`coach_knowledge.py`、`knowledge_runtime.py`、`rag/hybrid.py`、`schemas.py`、`prompts/knowledge_answer.md`、`tests/test_knowledge_loop.py`。评测脚本延续 `evals/` 与 `scripts/` 的已有组织。

### 第三步：E4a，建立反馈与候选审核

**最终行为：**用户指出回答不对时，可追踪到原问题、答案版本和证据；纠正进入相应候选范围，不立即变成通用知识。

- 新增受认证的反馈入口，分类为个人事实更正、检索未命中、证据不支持或来源过期，关联原会话/回答/来源版本，重复提交幂等。
- 个人更正留在本人范围并走 E2 确认流程；公共知识候选必须重新取得独立、可审核的公共出处。点赞、模型自评或旧模型答案不能单独充当事实证据。
- 候选保存出处、适用范围、作者/提取方式、版本、审核意见和评测报告。先实现候选创建、查看、驳回和修订，不因存在候选就加入在线召回。
- 精确哈希去重作为起点，语义近似仅用于提示人工检查；新旧来源相互冲突时标明待核对，不能通过相似度自动合并事实。

**验收：**其他用户不能读取/修改私人反馈；无来源、含私人信息、内容已更改或未通过检查的候选不能进入公共发布。模型只可建议候选，发布资格来自服务端授权与人工操作。

**代码入口：**沿用 `api/` + `services/` + Pydantic 的组织，在 `database.py` 增加必要的反馈/候选/审核记录；确切表名和索引在实现阶段设计，不提前宣称已建表。

### 第四步：E4b，评测门禁、发布和回滚

**最终行为：**审核通过的知识可在独立版本中评测，只有符合门禁并获授权批准后才可发布；错误版本能回滚并停止检索。

- 候选状态区分待核对、待评测、待审批、已发布、已驳回和已撤回；内容变化后旧评测与旧审批自动失效，禁止跨版本复用批准。
- 公共知识评测检查出处、适用范围、检索相关性、引用完整性和既有关键题退化；私人内容不进入公开语料、评测输出或公共向量缓存。
- 发布按版本装配来源清单、FTS 索引和向量缓存，完整构建后切换；中途失败保持上一版。撤回后旧缓存和答案快照均不能绕过来源有效性检查。
- 人工审核者权限由认证服务端决定；普通账号不能发布公共知识。第一版提供最小审核入口和发布脚本即可，不建设复杂管理平台。
- 至少演示一条“反馈→有出处候选→重复检测→评测失败或通过→审批→发布可检索→回滚后停止引用”的全链路。

**后续可选：**复用同一门禁流程审核离线产生的检索策略候选；只有实现开发/留出评测、批准、版本发布与回滚后，才使用“受控策略自提升”的表述。不把单次二轮检索称为跨请求学习，不以微调模型为本轮前提。

## 4. 简历口径与范围

- 技术栈写具体组件：Python、FastAPI、Pydantic、SQLite/FTS5、jieba、阿里云 Embedding/千问 API、SciPy（MILP/HiGHS）；RRF 可列为算法。Agent 工作流、Memory System 属于设计能力，不冒称某个已经接入的框架。
- 简介目标：面向饮食记录、餐次规划与训练建议，通过有界 Agent 工作流将文本、语音和饮食照片转为可核对草稿，结合用户确认的个人档案与可追溯知识证据生成建议。知识反馈审核闭环完成后再增加“受控知识沉淀”。
- 第二项使用“Pydantic 结构校验与业务规则复核”，不把类型校验说成语义判断；稳定个人事实由用户确认，幂等不等于 Agent 自主写入授权。
- 第四项保留为最终目标，但拆开说明个人事实治理与公共知识发布。更正和时效由状态/版本规则处理；公共资料不足才进入检索循环。正式简历只写验收完成部分。
- 复用现有 FastAPI/SQLite 服务、模型与索引；本轮不因名称引入 LangGraph、多自治 Agent、新向量数据库、自动联网补库或模型微调。不改变既有训练/饮食业务范围。
