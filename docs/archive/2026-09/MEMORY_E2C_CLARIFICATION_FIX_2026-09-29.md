# E2c：器械范围与补问修复（2026-09-29）

本轮修改实际业务处理，接续9月28日的固定评测。原题集、标签、真实调用记录和旧报告保留；本轮没有新增云模型调用，也没有更改正式数据库或部署。

## 用户现在会看到什么

| 输入 | 之前的问题 | 当前处理 |
| --- | --- | --- |
| 我训练的地方只有哑铃 | 模型默认session时，后端也会接受 | 返回范围未指定，用户选择本次/今天/长期后才能确认 |
| 训练的地方可能只有哑铃，还没确认 | 候选被校验拦截，接口返回502 | 显示具体补问，不展示可确认的器械候选，不应用训练修改 |
| 明天只有哑铃 | 把不支持的未来条件作为接口错误 | 请用户说明今天实际可用条件，未来条件不提前生效 |
| 平时只有哑铃，今天徒手 | 一个候选混合两种有效期，校验失败 | 要求分开核对，不静默丢掉其中一项 |

用户继续补充明确原话后，可以生成新的候选并手动确认。例如补充“我确认了，今天只有哑铃，没有训练凳”，当天事实可用于新会话；旧的补问草稿不能再确认。此前另行声明的食物禁忌等限制仍保留，解决器械疑问不等于清除全部待办。

## 为什么这样实现

模型负责把自然语言整理成结构化理解，业务层决定什么可以变成事实。此次把两种结果区分开：

- **需要用户补充**：器械不确定、未来日期、混合作用范围。返回可继续的`needs_input`状态，原话保留，确认和自动应用均不能通过。
- **不能信任的输出**：伪造来源、错误消息版本、值不在原话里、遗漏不可用器械。仍拒绝，不能因为有“不确定”几个字就放过这些错误。

具体时间词和不确定表达只是有限的保守校验，不是完整中文语义系统。它可能对包含多个话题或不确定修饰词的复杂句子多问一次；开放表达仍需真实模型和更丰富的独立题目验证。没有为本轮更换模型、重新分词或引入一套新的记忆框架。

## 代码分工

- `services/equipment_memory.py`：新增明确的`EquipmentNeedsInput`业务状态；先核对候选来源、原文和否定条件，再识别需要补问的时间/确定性。有效期从明确原话确定，缺少依据时一律保留`unspecified`，不接受模型替用户默认。
- `services/coach_reviews.py`：将该状态接入既有理解草稿；清除不能应用的训练修改和器械候选，保留原话及其他限制。旧的`training.equipment`和“在家，只有哑铃”短句兼容入口同样要求核对范围。仅有器械候选时才读取其日期，避免器械逻辑给餐次校验引入无关依赖。理解策略版本升至v14，使未确认的旧策略草稿不能复用；确认、并发指纹与身份隔离规则沿用现有实现。
- `prompts/coach_understanding.md`：明确未说明范围不得默认、不确定条件不产生事实候选、用户补充后重新依据新原话提取。此提示词改动尚未做新真实模型评测。
- `static/coach.js`：待补问时明确显示尚未应用任何修改，复用现有补问界面。
- `scripts/replay_memory_responses.py`：只把旧真实运行中的开发集结构化响应重新送入当前业务API，不重新生成答案，不读取标签来修正模型输出。没有响应的供应商失败逐条标为不可回放；不回放留出集，不覆盖旧报告。

没有新增schema、表或第三方依赖。

## 回放结果的正确读法

[完整回放报告](../../../evals/results/memory_v1_dev_replay_final_20260929/REPORT.md)记录了60个开发场景中的55个可回放场景。另5组没有取得可用模型响应，无法伪造其回放；原失败仍留在9月28日报告中。

| 同一批旧模型输出 | 原处理 | 当前处理 |
| --- | --- | --- |
| 正常进入补问 | 0/15 | 15/15 |
| 业务校验后候选严格匹配 | 35/40 | 40/40 |
| 模型原始候选严格匹配 | 29/40 | 29/40 |
| 最终建议器械及来源严格匹配 | 75/75 | 75/75 |

这些数字说明15次补问和5次未声明范围的处理得到修复。模型输出固定，因此原始提取成绩没有变化；最终建议在这批可回放题上原本已经通过，也没有新增提升。`no_false_candidate`仍为2/15，因为它同时检查模型原始输出；不能把后端丢弃错误候选记成模型没有生成错误候选。

这是一份开发集的后端回放结果，不是独立留出效果、新提示词效果或总体记忆准确率。9月28日真实报告中的87.50%与本次55组回放的分母不同，不能比较为“87.5%提升到100%”。
