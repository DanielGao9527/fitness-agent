# 架构与数据流

Fitness Agent 是一个单体 Web 应用：FastAPI 同时提供 API 和网页静态资源；前端使用原生 JavaScript，私人业务数据保存在 SQLite。语言、语音和照片理解通过后端按需调用模型，浏览器不持有供应商密钥。

```text
浏览器页面 static/
    ↓ 同源 HTTP，请求携带登录会话
FastAPI app.py / api/
    ↓ 校验参数与用户身份
业务服务 services/
    ├─ database.py → 私人 SQLite：账号、档案、记录、对话及草稿
    ├─ rag/ → 公共资料清单 + 独立 FTS5 索引 + 可选文档向量缓存
    ├─ data/nutrition、data/training → 审核候选和参考
    └─ model/ + prompts/ → 可选千问调用
```

## 模块职责

| 位置 | 职责 |
| --- | --- |
| `app.py`、`config.py` | 应用生命周期、环境配置、中间件和访问模式 |
| `api/`、`schemas.py` | 路由、输入校验、认证会话及返回契约 |
| `security.py` | 密码哈希、会话及认证相关工具 |
| `database.py` | 私人数据表、迁移及连接管理 |
| `services/` | 记录、目标、对话、推荐、营养配量和版本校验 |
| `model/` | 模型供应商适配、超时、结构化输出及错误分类 |
| `prompts/` | 应用调用模型时使用的任务提示词 |
| `rag/` | 审核资料加载、检索、有效期与出处检查 |
| `agent/` | 有界工具适配及早期通用接口兼容；当前助手编排主要在 services |
| `static/` | 页面、表单、对话、草稿保护与错误呈现 |

## 记录与建议

饮食、训练和体测只有用户明确保存才成为实际记录。AI 解析、营养估算和助手推荐是待核对内容；生成建议不会自动写入实际记录。幂等键防止重试重复写入，版本和事实指纹用于拒绝过时结果。

身份始终来自已认证会话，接口不信任请求正文或模型生成的 `user_id`。按用户隔离数据，模型返回后再次核对用户归属、输入版本和相关条件。

## 饮食与目标

用户描述先形成待确认草稿，估算保留范围、假设和来源。目标来自已保存档案及用户明确选择的调整，今日覆盖优先。配餐由审核候选、模型选材与本地数值求解配合，最终重新检查营养区间、过敏禁忌、食材选择和修改范围。

已吃记录与建议分开计算。未知营养不当作零；无法满足约束时说明缺口，保留原建议，不伪造达标结果或无条件重复调用。周期反馈是有界工程估算，不声称测得真实全天消耗。

## 训练建议

当前提供三、四、五分化下的当天建议，结合已保存档案、明确器械、时间及本人近七日实际完成内容。组次受结构、经验与时间限制；可用时间与预计训练时长分开显示。

部分历史接口和数据仍为兼容保留，不代表页面继续开放旧周计划。实际记录、建议和可选历史负重参考分别处理；没有可比较事实时不猜初始重量或自动加重。

## 知识与模型

### 个人对话回忆 E2a

`services/coach_memory.py` 在现有本人对话表上有界扫描经核对的旧原话，jieba 词项找回最多几条带日期与来源 ID 的历史证据；`api/coach.py` 提供认证后的私有搜索。当前待理解消息明确指向“上次”等旧对话时，`coach_reviews.py` 将证据作为历史上下文传给理解模型，确认与实际记录仍由原业务路径负责。删除对话立即移除可检索来源；私人历史不进入公共知识向量库。实现边界见 [E2a 说明](../MEMORY_E2A.md)。

### 用户确认的温记忆与历史摘要候选 E2b

schema v15 在私人库新增 `coach_memory_entries` 和 `coach_memory_digests`。前者由用户在聊天页明确保存、修改或删除交流偏好与个人术语，每账号最多 20 条、合计 1200 字；不承载过敏、器械等档案硬约束。理解模型调用前读取当前账号条目到 `warm_memory`，与档案、本轮待办、旧对话证据分开标记，模型返回时通过上下文指纹检查版本变化。公共知识摘答不读取此私有记忆。

后者按需将某段对话最新最多三条**已核对原话**拼成带来源轮次的摘要候选，不用模型补写事实。用户核对后才能用于“上次”等指代的旧证据找回，不能自动变成今天的限制；来源变化使旧摘要失效，删除原对话会级联删除摘要。个人资料与摘要不进入公共知识 FTS/向量缓存。E2b 当前实现和未覆盖项见 [记忆进度](../MEMORY_E2_DESIGN.md)。

### E2c 已确认器械到最终建议

2026-09-29理解策略v14区分器械业务补问与不可信模型输出。`EquipmentNeedsInput`仅表达有来源但不确定、未来/混合时段或过期当天条件；`coach_reviews`将其转为`needs_input`，不提供可应用的器械候选或训练修改。来源版本、原话、否定条件不完整仍拒绝。明确时间词确定候选范围，无依据则为`unspecified`，必须人工选择；旧`training.equipment`入口执行相同补问检查。未确认旧策略草稿因指纹变化失效。无schema变更，说明与验证见 [补问修复](../MEMORY_E2C_CLARIFICATION_FIX_2026-09-29.md)。

离线质量验收由 `scripts/evaluate_memory.py` 驱动：读取 `evals/memory/` 的冻结场景和独立器械标注，每组建立临时私人库/账号，经过真实业务API完成理解、人工确认、建议及更正失效。`annotated`为标注模型替身，`live`为应用原提示词的真实千问调用；后者必须显式给调用预算，失败计入且不自动重试。提取、校验后候选、数据写入边界和最终建议分别判分，结果由 `report_memory_evaluation.py` 合并不重复分片。评测不接正式库，不新增生产schema；范围和实际结果见 [E2c评测](../MEMORY_E2C_EVALUATION.md)。

E2d.1 在这条链路加入私人 schema v16 的 `profile_fact_events`。器械值仍由 `profiles.equipment` 单独管理，事件只保存版本与来源元数据。档案保存与对话确认由 `profile_facts.write_profile` 原子写入；同值重复保存不增版本，清空会递增。`training_context` 同时绑定器械字段版本，理解/建议指纹、已核对器械原话及摘要也检查版本，避免 A→B→A 令旧内容复活。档案页面带快照版本提交，过期请求整笔拒绝；旧 API 无请求头时保留显式保存兼容。删除聊天只使来源引用不可用，独立确认的档案需另行撤销。范围、迁移与验收见 [E2d.1](../MEMORY_E2D_FACT_VERSIONS.md)。

E2d.2 当前结构升到 v17（24 表）：`coach_day_equipment` 保存每账号唯一的当前当天器械、日期、递增版本和来源。原理解调用可输出带完整原话的 `equipment_memory`；业务校验后由用户选择本次/今天/长期并确认，自动理解不消费此候选。本次条件最晚当日结束，今天条件只用于北京时间当天的会话，长期使用现有档案。有效本次条件优先于当天条件，再读取档案；版本及日期进入理解/建议指纹，动作替换绑定器械版本。临时器械不作为跨会话冷证据或摘要，长期语义原话绑定档案版本。删除当天来源对话清空当天值并保留版本计数；独立确认的长期档案仍需单独撤销。详见 [E2d.2](../MEMORY_E2D_SCOPES.md)。

`services/coach_memory.py` 只识别少量无时间限定、器械可校验的明确句式。`coach_reviews.py` 在理解草稿里标出“确认后写入档案”的器械，用户手动确认才将它写入本人 `profiles.equipment`；自动理解不会隐式改长期档案。`training_recommendations.py` 每次生成建议读取当前档案和本轮条件；`training_context.py` 用档案快照锚定本轮器械，档案后来更正时移除旧会话器械。旧原话与审核摘要的检索在器械与现档案冲突时抑制该来源，原对话仍作为历史留存。单场景真实千问理解、跨会话建议和更正后再建议已在临时合成账号验证，更多自然语言变体与质量评测未完成。

公共资料是带出处、审核状态、范围和复核期限的清单。FTS5 索引与私人记录分离；应用运行时不自动从网络补齐知识，不把私人档案写入公共知识库。详情见 [资料说明](../../../KNOWLEDGE_SOURCES.md)。

### 默认混合检索

应用默认以 jieba 搜索分词驱动 `LocalKnowledgeRetriever` 的 FTS5/BM25，再与向量结果融合；中文相邻双字仍可显式配置用于旧基线。`sections` 是已有人工审核块，FTS5 与 jieba 不负责重切文档。

`model/embeddings.py` 独立调用 DashScope 原生向量接口，区分 `document` 和 `query`；两路统一使用标题、摘要和关键词字段。`rag/vector_store.py` 只通过显式构建写入公共文档的 float32 向量，绑定模型身份、维度、文本模板和内容哈希。构建失败保留原版本，不覆盖私人数据库。应用启动、目录查询与按 ID 读取证据都不会远程编码文档。

`rag/hybrid.py` 在有效缓存上执行精确余弦检索，再与词法候选进行等权 RRF 融合。缺少缓存、内容不匹配或向量不可用时返回明确的词法降级元数据；来源撤回、过期和删除立即过滤，不能靠旧向量继续返回资料。查询原文和查询向量不写入生产文档缓存。

`services/knowledge_runtime.py` 将问题编码绑定已认证用户的调用额度。知识服务每次检索冻结一份 `RetrievalSnapshot`，包含候选及允许公开的模式、版本和排名信息；最终摘答按 ID 与内容复核，不用再次排序代替来源校验。配餐、训练仍按固定 ID 取证据；旧通用 Agent 预览和关闭接口保持词法路径。实现及离线评测见[检索增强](../RETRIEVAL_ENHANCEMENT.md)和[题集说明](../../../../evals/README.md)。

默认 hybrid 但没有服务端密钥时，应用构建无向量提供者的检索器；目录和查询分别报告 `embedding_not_configured`，后者使用 jieba 词法结果。`scripts/start.ps1` 默认覆盖继承的旧环境变量为 `hybrid + jieba`，`-UseLexicalBaseline` 只用于旧对照；启动不自动构建向量缓存。

### E3a 有界检索自纠正

`services/knowledge_answers.py` 在第一次候选与受约束证据判断之后，只有 `insufficient` 且模型给出有效改写时才追加一次检索与判断。第二轮仍用用户原问题判断证据；改写不能改变范围，重现相同候选或达到两轮上限即停止。每次云端问题编码和模型判断均通过原认证额度；来源变化继续按稳定 ID 拦截。主聊天第二轮仍执行对话限制及营养禁忌检查。响应仅保留公开候选 ID、阶段、降级与停机原因，不保存改写后的私人问题或向量。合成回放用 `tests/test_knowledge_loop.py`，不是在线质量提升评测。

模型能力可独立关闭。缺少配置时账号和手动记录仍可运行，AI 接口返回明确状态。请求设超时与次数限制，失败不自动重试；这些限制不等于供应商账单的绝对金额上限。

### 主聊天知识分流

主聊天的 `request_kind/action` 表示本条消息的动作，`intent` 保留原会话的配餐或训练任务。明确的一般问题走保守的本地语句规则；其他口语由受约束的 `CoachUnderstanding` 识别，新增 `knowledge` 类型只负责分类，不生成知识答案。混合知识、个人限制与安排的输入需要澄清，不静默选择其中一项。

`api/coach.py → services/coach_knowledge.py → services/knowledge_answers.py` 复用审核摘答：只选择本次候选摘要，复查来源有效性，前端在原聊天里呈现正文和出处。不联网抓取或扩库，也不把知识回答升级为个体处方；启用混合检索时仅按需调用向量服务。一般问题不要求配餐确认；实际配餐仍需独立授权与摄入校验。

知识请求与结果保存在既有 `coach_turns.response` JSON 内，无新增表或数据库版本升级。`version` 检测所有消息并发变化，`workflow_version` 排除只读知识轮次，保留原计划绑定；推荐接口拒绝把当前知识轮次当成新计划请求。待办按 `reviewed_versions` 逐条处理，不再以最大已确认版本跳过历史消息。确认知识理解只处理当前知识消息，旧未核对条件仍暂停相关操作。

每条主聊天知识消息只启动一次有界知识工作流：直接证据足够时一次问题编码和一次证据判断；第一次判断不足且建议有效改写时，最多再各调用一次。前置口语理解可能另有一次调用。每次真实远程尝试共用账号、游客和全站额度。重复 HTTP 请求复用生成中、成功或失败状态；进程中断时不假定外部调用未发生，不自动重试。重新提问才是新尝试。返回前校验消息版本、档案与条件，刷新历史时再核对引用的有效性。向量调用只上传公开文档或本次问题改写；摘答上传原问题和公开候选摘要，不上传完整档案或私人记录。

范围保护仍保守：档案含敏感健康条件时暂停一般摘答；营养问题涉及已有食物过敏/禁忌时不判断本人适用性。会话中尚未核对的条件也不会因知识分流被遗忘。明确区分未启用、限额、资料不足、范围不适用、待办未核对、索引故障、供应商异常及来源变化。

## 部署边界

共享模式要求明确 HTTPS 域名、Host 白名单和安全 Cookie；注册与游客是独立开关，不再强制关闭注册。关闭交互式调试文档，匿名健康接口不返回具体模型型号。认证后的建议结果保留来源元数据。应用以单 worker 运行，SQLite 与模型 Key 位于发布目录之外。反向代理只访问本机应用端口，见 [部署说明](../../../DEPLOYMENT.md)。

## 账号与游客

正式账号保持密码哈希与七天登录会话。游客使用不能密码登录的临时账号，数据仍由服务端会话隔离；额外校验当前页面的随机证明，仅哈希入库。浏览器会话Cookie保持HttpOnly，页面证明只在sessionStorage/内存，普通刷新可继续，新访问不恢复。关闭/恢复标签页并不提供可靠的服务器通知，最终以服务端有效期为准。

v14新增guest_accounts与guest_usage两表，不改写原业务行。游客两小时无有效请求失效，最长一天；启动时及每分钟清理过期账号，通过外键清理其档案、记录、对话及草稿，退出立即清理。临时账号随机负ID与正式账号正ID分区，避免清理后较晚返回的请求误写到随后注册的人。guest_usage仅保存日期、网络地址哈希与计数，删除游客不退还额度；合计正式账号计数与游客聚合计数，避免重复计入或删除后归零，旧计数保留七天。网络地址由可信代理后的request.client提供，不信任客户端自行提交的user_id或转发头。

共享模式下任何低于当前 v15 的旧库都会被自动部署预检拒绝；先人工停服、做独立校验备份、执行离线迁移并复核表指纹，再恢复自动更新。安装在服务器的固定 check_release.py 需要经管理员审核更新，不能只推送仓库后假定配置已经生效。完整边界见[账号与游客](../../../ACCOUNTS.md)与[运行恢复](../../../OPERATIONS.md)。

应用面向一般成人健身记录与建议，不提供医疗、伤病康复处方、支付、社交或穿戴设备接入。
