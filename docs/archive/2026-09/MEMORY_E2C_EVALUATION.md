后续修复已于2026-09-29接入，见 [范围与补问修复](MEMORY_E2C_CLARIFICATION_FIX_2026-09-29.md)。下文是保留的9月28日基线结果；新结果只重放开发集的旧模型输出，不覆盖本报告或声称真实模型重新测出提升。

本增量交付可复现的记忆评测入口及固定业务场景，复用已完成的 E2d.1/E2d.2 代码。生产记忆逻辑、模型提示词和正式数据库未因这次评测改写。首轮真实结果已保存；供应商连续三次计费类别403后停止，仍有2组未运行，不能宣称100组真实全测完。

## 为什么还要做这一轮

上一轮测试证明：给定正确候选，程序能确认、保存、跨会话采用、处理更正和到期。但真实千问可能把“今天”理解为“本次”，遗漏否定，或没有生成可核对的候选。这需要真实模型经过同一业务接口完成后再判分。

评测分三个层次：

1. 模型输出：范围、器械摘录及来源是否符合预先标注。
2. 程序行为：候选是否经过核对，未确认是否改了档案，旧版本是否拒绝，个人数据是否隔离。
3. 最终建议：器械与来源是否正确，动作需要的设备是否真的可用，条件失效后是否停止沿用。

例如原话“今天换地方训练了，只有瑜伽垫”，模型可能输出 `session`，程序根据“今天”更正为 `day`。原始提取与校验后的候选必须分别统计，不能因为最终成功就把前面的模型错误抹掉。本版同时保留严格文本匹配和实际动作器械检查；前者可能因同义措辞扣分，不能直接叫通用语义准确率。

## 题集与公开基准的关系

当前固定 **100组＝20个场景族×5种器械变体**，开发60组、留出40组，按完整场景族划分。包含长期/当天/本次、用户选择范围、未确认、更正/清空、零点到期、A→B→A、来源删除、重启、跨账号和理解期间更正。

题集和标签由本轮开发助手编写，是自建合成集；没有独立人工复核，不是100个独立真实用户样本。完整标签与哈希见 [题集说明](../../../evals/memory/README.md)、[固定输入](../../../evals/memory/cases.jsonl)、[版本清单](../../../evals/memory/manifest.json)。所有标注在真实运行前冻结，结果不好不会删题或改答案。

查阅了 [LongMemEval](https://github.com/xiaowu0162/LongMemEval) 的信息提取、多会话、知识更新、时间推理及拒答维度，以及 [LoCoMo](https://github.com/snap-research/locomo) 的长时对话评测。这里借鉴评测维度，没有复制或运行其官方题目。它们不能直接替代本项目的数据库确认、到期和最终建议验收。本版也没有评测长历史噪声检索和其他偏好，不能冒充完整长期记忆基准。

## 代码与数据流

- `evals/memory/build_cases.py`：保留题目编写源；`cases.jsonl`和`manifest.json`提供冻结输入与哈希，已有版本拒绝覆盖。
- `evals/memory/protocol.py`：核对数据和集合边界，按外部标注判分。没有用生产器械解析器生成标准答案，也不调用另一个LLM给自己打分。
- `scripts/evaluate_memory.py`：每组临时库/账号，经实际API执行消息、理解、确认、建议、更正、删除、重启和跨账号操作。模型使用应用原提示词，仅收到正常应用上下文，不收到题集标准答案。结束即清理临时库。
- `scripts/report_memory_evaluation.py`：合并互不重叠的运行分片，要求语料、生产源码、判分协议、模型模式和型号一致。重复题目拒绝合并，不能选更好的一次；模拟与真实结果不能混在一起。
- `tests/test_memory_evaluation.py`：验证不向真实模型泄漏标签、调用失败计数、预算停止、失败仍在分母、禁止覆盖结果、禁止重复/混合分片等评测本身的约束。

`annotated`模式把标注喂给模型替身，只检验接线。`live`模式才调用千问。两者均不修改正式档案、不写实际饮食/训练、不调用向量服务，不需要启动正式服务或浏览器。公共证据使用既有本地词法检索，评测的是记忆，不能据此宣传新检索提升。

每次调用前写入attempt记录，返回后写入response或failure；所有失败计入预算，无自动重试。连续3次供应商错误会停止后续题目。输出按原始题目保留，不只保留成功部分。记录调用耗时，不捏造token或金额；本次尚无旧版本匹配对照，所以没有“增强前后提升X%”。

## 已定位的开发集问题与修复入口

以下只分析开发集；不根据留出集逐题改提示词或标签。

| 开发集例子 | 本轮观察 | 下一步修改方向 |
| --- | --- | --- |
| `day_cross_session-03`、`day_expiry-01` | 模型把“今天/今晚”标成session；服务器纠正为day，确认后建议及跨天失效正确 | 保留服务器校验；模型原始提取仍记失败，不能将最终成功当成模型满分 |
| `scope_choice-01` | 未声明范围，模型默认session；当前校验接受该范围，后续动作与人工选择一致 | `equipment_memory.candidate_from_model`对没有原话依据的范围保留unspecified，要求用户选择；不只防止误存长期 |
| `uncertain_claim-01` | 模型对“可能……还没确认”同时给出候选与追问，候选校验返回502 | 候选不提升为当前事实；区分需要澄清的业务输入与模型结构/来源错误，前者进入可回答的补问状态 |
| `future_condition-01` | 对“明天……今天还不确定”生成候选，后端拦截并返回502 | 保留未来条件不可提前应用的限制，改进补问接线，不放宽为今天有效 |
| `mixed_scopes-01` | 一个候选混入长期与当天条件，后端拦截并返回502 | 拆开核对不同作用时段，不能静默取其一；先支持一次一个候选的补问流程 |

这些不是“去掉校验就能涨分”的问题。应在 `services/equipment_memory.py` 和 `services/coach_reviews.py` 区分**需要用户补充**与**无法信任的模型输出**，配合 `prompts/coach_understanding.md` 收紧提取约定。补问仍不写事实，伪造来源、遗漏否定和版本过期仍必须拒绝。改动后先用固定的开发失败回放验证，不在旧留出集上挑选最优版本。

本轮仅交付评测工具和问题定位，没有修改上述生产处理；因此旧结果能作为后续修复的源码版本基线。没有旧版记忆系统的匹配对照，暂不填写记忆“提升多少”。
