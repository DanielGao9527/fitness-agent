# 账号、注册与游客

## 当前行为

- 登录：已有账号的档案与记录长期保留，密码不明文存储。
- 注册：开启FITNESS_REGISTRATION_ENABLED后显示入口，完成注册即登录。共享HTTPS模式不再强制关闭注册，关闭开关仍保留已有用户登录。
- 游客体验：无需用户名密码，创建独立临时账号，使用同一套档案、记录和已启用AI能力。不会读取或复制管理员的记录，也不是所有人共享一个演示账号。

正常刷新保留本次体验，新的页面访问不自动进入旧游客；主动退出立即清理临时业务行。两小时未使用或满一天后失效，后台每分钟清理，停机后下次启动清理。不能保证关闭浏览器瞬间删除，浏览器恢复标签页也不能作为安全期限；最终以服务端过期判断为准。禁用浏览器临时存储时仍能体验，但刷新可能需要重新开始。暂不支持游客数据转存正式账号，需长期保存应先注册。

## 次数与隔离

游客AI默认同一网络每日20次，同时受已有账号上限和全站上限约束；失败也计次，不自动重试。同一网络创建游客每15分钟最多10次，全站每15分钟最多200次；这是有限防滥用，不是验证码或防攻击服务。共享网络可能共用额度，换网络也不能绕过全站总额。代理只信任本机Caddy，不能信任任意X-Forwarded-For。

退出、到期、重启或重新创建游客都不会重置已消耗的全站/网络额度。计数不包含食物、训练、聊天正文；详细保留边界见[隐私说明](PRIVACY.md)。手动记录不消耗模型次数。

## 已有服务器的一次升级

当前数据库由v13升为v14，增加guest_accounts与guest_usage；正式账号、密码哈希、历史业务行不改写。新代码支持读取v13/v14备份，初始化前保留pre-v14副本。备份不是自动回退：旧v13程序不能运行v14库。

因此先推送功能分支检查，不直接合并main触发自动部署。由服务器维护者安排以下维护步骤：

1. 暂停fitness-agent-pull.timer和GitHub的DEPLOY_ENABLED，确认没有正在执行的部署；确定通过检查的新提交及维护窗口。
2. 在独立目录准备该固定提交和Python依赖，核对测试。审核并更新固定安装的deploy/check_release.py：旧版始终要求注册关闭，新版核对注册和游客是否与配置一致。不要用不明版本脚本覆盖服务器工具。
3. 停止fitness-agent，使用私密新路径创建并验证v13一致性备份。使用候选版本的scripts/migrate_guests.py显式执行迁移，参数见下文；迁移前后旧业务表指纹必须一致。
4. 配置候选v14版本为当前版本，完成systemd、本机健康、HTTPS登录、已有记录、注册、游客隔离与清理核验。此步骤是人工维护，不使用旧v13作为失败自动回退目标；失败时保持维护状态，结合已核实备份处理，不能强启旧代码。
5. 确认服务器运行同一个经过检查的v14提交后，再协调main/deploy提交与last-successful-sha，恢复原发布器流程。不要手工强推deploy或伪造成功记录；由现有发布流程确认提交。之后同结构更新继续正常自动发布。

迁移工具必须在停止应用、暂停部署后使用，并用候选版本解释器执行；这里的路径仅是占位符，不是已执行命令：

```bash
/path/to/reviewed-v14/.venv/bin/python /path/to/reviewed-v14/scripts/migrate_guests.py \
  --database /var/lib/fitness-agent/fitness.sqlite3 \
  --backup /var/lib/fitness-agent/backups/before-guest-upgrade.sqlite3 \
  --confirm-service-stopped
```

不要从聊天或公开仓库复制真实数据库或密钥。该工具不停止服务、不切换代码、不改服务器配置、不访问模型；运行账户须有读写数据库和备份目录的权限。若任何一步失败，保留备份和报错状态，由维护者核对后再操作。

服务器环境文件需显式调整下列开关，保留原来的HTTPS、模型Key和全站额度：

```ini
FITNESS_REGISTRATION_ENABLED=true
FITNESS_GUEST_ENABLED=true
FITNESS_GUEST_AI_DAILY_LIMIT=20
```

共享模式未配置游客开关时默认关闭。修改环境后重启才生效；代码推送不修改/etc/fitness-agent.env。GitHub测试通过、发布分支推进、本机健康、真实公网体验是不同验证，不互相代替。
