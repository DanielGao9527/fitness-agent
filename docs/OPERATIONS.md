# 运维与恢复

以下数据库命令使用项目虚拟环境中的 Python；在项目根目录执行。`data/runtime` 是本地默认路径，云端应替换为实际持久数据路径。备份包含私人记录，不进入 Git、网页静态目录或公开附件。

## 健康检查与服务

`GET /api/health` 可核对应用启动和能力配置状态，不会生成 AI 内容。`configured_unverified` 表示配置存在，不等于真实供应商调用已经验证。共享模式不返回开发版本或具体模型信息。

Linux 服务、日志和自动更新命令见 [deploy/README.md](../deploy/README.md)。修改环境变量后重新启动服务；不要仅因页面可打开就宣布模型网络连通。

## 私密创建账号

共享服务保持 `FITNESS_REGISTRATION_ENABLED=false`。首次正常启动服务生成空数据库后，在自己的 SSH 或云控制台交互终端执行：

```bash
sudo -u fitness /opt/fitness-agent/current/.venv/bin/python /opt/fitness-agent/current/scripts/create_account.py --database /var/lib/fitness-agent/fitness.sqlite3
```

输入用户名，再输入两次密码，密码不会显示。用户名为 3–32 位字母、数字或下划线，密码为 8–128 位；创建完成后从网页登录即可。工具只连接指定的已有应用数据库，不发登录会话、不修改已有账号、不开放网页注册。密码不接受命令参数、环境变量或管道输入；由账号使用者在私密终端输入，不发送到聊天或写入脚本。

## 一致性备份

```bash
python scripts/backup.py create --source data/runtime/fitness.sqlite3 --destination data/runtime/backups/manual-001.sqlite3
python scripts/backup.py verify --source data/runtime/backups/manual-001.sqlite3
```

工具使用 SQLite backup 接口处理运行中的已提交内容，同时生成清单并检查完整性/外键。目标必须是新路径，保留同名 `.manifest.json`；不要直接复制运行中的主文件，或手动删除 WAL/SHM。

备份未自动加密，哈希也不是来源签名；只恢复自己可信保管的副本。单机磁盘副本无法防止整机损坏，正式服务还应配置私密异地备份、保留周期与定期恢复演练。

本机原库已于 2026-10-15 在私密备份、升级副本及恢复演练后由 v19 升到 v20（32 表）；原 28 表所有原字段在迁移和启动后指纹一致，新增四表为空。此为历史升级；当前本机运行 e4b2b2-knowledge-publication-v22，最新状态见 EXECUTION。没有自动授予实际账号审核权限。私人库、备份与日志不进入 Git，未操作公网环境。

v19 新增本人反馈、摘录候选和候选事件三表，不向公共索引发布内容。此前 v18 的笔记分类、来源和集合版本继续保留；v17→v18 的备份及历史核验见原有私密备份目录 memory-provenance-20261014-93b01a2e。

其他尚未升级环境先停服，确认源库为 v14–v21，选择全新的私密备份路径：

~~~text
python scripts/migrate_memory.py --database <现有库绝对路径> --backup <新备份绝对路径> --confirm-service-stopped
~~~

沿用原迁移入口，当前目标为 v22（38 表）；v20 新增四张审核表，v21 再新增登记、提交成员及版本事件三表，不修改原业务字段。工具创建并验证一致性备份，升级后按原字段投影核对业务行；加列不能直接比较 SELECT * 的整行形状。发布器要求实际库与候选代码的完整结构相同，不能绕过预检自动升级。

命令不停止或重启服务，不自动回滚。普通启动旧库会执行初始化升级并留下 pre-v22.bak，但它不能代替独立校验备份。v13 沿用账号与游客旧库工具，目标同样随当前代码升级。升级后演练恢复并验证记录，再切换服务；不要让旧程序操作 v22 库，也不要以旧备份覆盖新增记录。

## 公共摘录审核权限

默认所有账号均没有审核权限。账号使用者在私人终端选择一个已有正式账号，使用当前项目的 Python 执行（数据库必须是已有 v20/v21/v22 库的绝对路径）：

~~~text
python scripts/knowledge_reviewer.py grant --database <私人库绝对路径> --username <已有用户名>
python scripts/knowledge_reviewer.py revoke --database <私人库绝对路径> --username <已有用户名>
~~~

工具不会创建账号、升级数据库、发放登录会话或发布知识，拒绝游客及不存在账号。重授已启用权限不增加版本；撤销会使该审核人此前通过的预审失效，再授予不会复活旧批准。没有网页提权接口，不以第一个注册账号作为默认管理员。项目为个人使用，未要求双人分权；若同一人提交和审核，不能对外声称完成独立双人复核。

用户在助手工作台显式提交后，审核人才看到公共摘录及出处；私人对话和反馈不共享。检查通过仅代表出处与检索工程检查，人工预审仍不发布；语义质量、核心题回归、不可变版本构建和回滚见 ROADMAP 的 E4b.2。来源文件变化在读取时核对，不提供对外部文件瞬时修改的持续监控保证。

## 候选知识版本构建

在助手的“公共摘录提交与预审”中，具有审核权限的正式账号选择有效预审提交，明确确认后构建。产物保存在私人数据库旁 knowledge-builds/UUID，每包包含 sources.json、knowledge.sqlite3、knowledge-vectors.sqlite3、regression.json 和 manifest.json；仍标记“已构建，未发布”，不切在线库。

只复用同模型、维度、模板及完整编码内容哈希匹配的已有文档向量；完整摘要重复时去重。缺短摘录向量会停止，没有自动编码或费用。独立语义与混合排名尚未验收，不能靠已有开发题词法检查批准发布。

构建前后重查权限、来源、提交/检查版本和日期；损坏文件不可用，临时目录失败清理，先前包保留。失败记录为 failed-UUID.json，词法退化记录含公开案例 ID 和判定，不含问题或私人正文。上限为 20 个成功包、50 个失败记录；归档/清理由本机管理员在确认绝对路径位于这个私密目录后执行，不通过网页传任意文件路径。删除反馈/对话/账号不会自动删除历史包，但会使其不能继续发布。

E4b.2a 批次私人库为 v20，无 schema 迁移。10 月 15 日在备份及恢复演练后激活 e4b2a-candidate-build-v20，原 32 表所有原字段指纹一致；备份在外层 data/runtime/backups/knowledge-builds-20261015-be543056。没有实际账号提权、实际构建或公网发布。

## 恢复到新路径

```bash
python scripts/backup.py restore --source data/runtime/backups/manual-001.sqlite3 --destination data/runtime/recovered-001.sqlite3
python scripts/rehearse_recovery.py --source data/runtime/fitness.sqlite3 --directory data/runtime/backups/rehearsal-001
```

恢复工具不覆盖现有库。恢复副本中的旧会话及会话级确认会失效，需要重新登录；账号、记录和快照内的调用计数保留。备份之后新增的记录不会自动出现，不能通过回滚清除实际发生的调用费用。

本地运行或未采用本项目发布器的自部署环境：真正切换恢复库前先停服，保存现状，核对恢复副本与备份后的新增记录，再按该环境的配置方式设置 `FITNESS_DB_PATH` 指向新文件并重启。

采用本项目 `deploy/` 发布器的生产环境：数据库固定为 `/var/lib/fitness-agent/fitness.sqlite3`，不能通过修改 `FITNESS_DB_PATH` 绕过发布器的路径校验。恢复前先暂停自动拉取，确认没有部署任务正在运行，再停止应用并保全现有数据库及相关文件。核对恢复副本的结构、完整性、账号、记录和调用计数，确认如何处理备份后的新增数据后，由管理员按单独审核的恢复方案在固定路径切换数据库，并保持 `fitness` 用户的所有权与私密访问权限。重新启动后验证健康、登录及记录持久化，再恢复自动拉取；不要直接覆盖正在运行的数据库。

上述演练命令只生成独立副本，不切换正式数据库。代码回退也不自动执行数据库恢复。

## 版本登记、检查与撤回

审核人可在构建列表下核对具体版本并登记，再查看发布准备报告；登记与撤回均需页面明确确认。登记准备检查列出未满足项，不能据此自动上线；完整质量报告通过后才可走下一节的批准与切换。上传报告或单独勾选框不能绕过门禁。

已撤回/失效登记不会重新启用；资料或权限更改需重新走提交、预审与构建。到期或协议变化也要求重建。登记最多 20 个；归档前先备份私人数据库，并协调登记与对应构建目录，不只删目录后尝试复活旧编号。

本轮原库副本 v20→v21 与恢复演练通过，原 32 表全部原字段保留；私密备份在外层 data/runtime/backups/knowledge-releases-20261015-ed050b84。进程检查改用普通权限的只读进程快照与命令行核对；停止服务权限审核重试后通过。实际原库已升级至 v21，重启后原 32 表所有原字段一致，三张登记表为空；运行 e4b2b1-release-registry-v21，没有实际提权、登记、云调用或公网发布。

## 已批准版本切换与回滚

当前本机已运行 e4b2b2-knowledge-publication-v22。独立备份及升级/恢复演练在外层 data/runtime/backups/knowledge-publications-20261015-db3f46b0；原 35 表原字段在迁移和重启后指纹一致。批准/切换事件为空，指针初始为原库，没有实际提权或候选发布。

具备审核权限后，先运行版本质量检查。正常 release_quality/v1 标签仍待独立复核，缺复核或匹配的问题编码时不能批准；0.80 是预先选择的检索验收下限，不是效果成绩。协议/真实预算流程见 [发布质量协议](../evals/release_quality/v1/README.md)。不要把 tests 的合成凭据放进正常协议。

通过后分别确认批准和切换。回滚可以选择曾上线且仍有效的批准版本，或原审核库；已经撤回/失效的版本不能恢复。撤回当前版本会切回原库。外部文件变化在读取时验源，旧浏览器内容须刷新后核对，不承诺后台抹除已显示文字。

私人数据库备份保留指针与批准，但不自动打包公共构建目录及问题编码缓存；恢复时需要配套有效文件。缺失/不匹配的版本会停止使用，保留原审核库路径，不能靠数据库里曾有批准继续引用旧包。没有自动云编码或静默补齐。

## 日期、限流与日志

业务日期按北京时间，AI 日次数按 UTC 日（北京时间 08:00 更新）。失败请求也可能消耗一次尝试；次数不是金额。登录限流状态持久化在私人库旁的独立数据库，不能删除它来绕过限制。

日志用于状态与故障定位，不主动输出密码、API Key、模型请求正文或私人记录。排障分享日志前仍需人工复核；供应商诊断使用安全故障编号和固定分类，不能根据通用错误提示推断真实根因。
